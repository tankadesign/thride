## Post-round fix: per-pane Perspective PSR memory

- **Bug (user-reported):** looking through a scene camera and switching back to "Perspective" showed the scene camera's last PSR. Cause: `rigFor` mapped scene-camera bindings onto the pane's `persp` rig (shared key), and `syncSceneCamera` overwrote that rig's transform every frame. Fix: rigs are keyed by the full binding (`pane:cameraId`), so scene-camera panes get their own rig and each pane's Perspective rig keeps its own PSR memory. Verified live: orbit → look through camera → back to Perspective restores position/rotation exactly.

## Post-round: Active Camera nav writeback + Display > Lines toggle

- **Active Camera nav (user-reported):** navigating (orbit/pan/dolly-drag/wheel) in a pane bound to a scene camera did nothing useful — `syncSceneCamera()` re-pulled the rig's transform from the camera node every frame, stomping any nav change made to the rig. Fix: nav on such a pane now writes back into the actual camera node's transform. Drags (`orbit`/`pan`/`dolly`) use the same preview→commit `TransformDragSession` the gizmo uses (`ViewportSystem.beginCameraNav/updateCameraNav/commitCameraNav`, wired from `ViewportInput`'s existing nav pointerdown/move/up) — one undo step per drag. Wheel ticks push a `SetTransformCommand` per tick (`applyCameraNavTick`), coalesced into one undo step by `History`'s tryMerge window. `syncSceneCamera` still pulls node→rig every frame, but it's now idempotent since nav keeps the node in sync. Verified live: created a camera node, bound pane 0 to it, pan/orbit/wheel-dolly all persisted into the node's transform (rig position matched exactly, no snap-back on subsequent frames), single "Transform" undo step per drag restored exactly.
- **Display > Lines toggle:** wireframe overlay on top of PBR/Flat shading, off by default (`PaneDisplay.lines`). Implemented as a permanent-but-hidden `LINES_MAT` (polygon-offset wireframe, semi-transparent) child mesh per mesh object in `SceneSynchronizer` (`linesOverlays` map, mirrors the existing per-node outline-mesh pattern), geometry kept in sync on rebuild, visibility toggled per-pane in `applyShading(mode, backfaces, lines)`. Disabled (no effect) in Wireframe mode since it's already all lines — verified the menu item shows `menu-disabled` when `shading === "wireframe"`. Verified live: toggling Lines on a PBR cube shows the triangulation wireframe overlaid on the shaded surface.

## Post-round: local autosave persistence + Lights subnav clipping fix

- **Local project persistence (user-reported):** projects were lost on every browser refresh (`App.tsx` always seeded a fresh Cube). Added `src/io/storage/local.ts` — interim persistence ahead of the real .thride package (H1): the whole document DTO autosaves to `localStorage` (debounced 400ms on every "scene" slice bump, plus a `beforeunload` flush so the last edit before a refresh isn't lost). `App.tsx` now tries `loadLocalProject()` before falling back to the seeded cube, and starts `startAutosave(doc)` in an effect. Known limitation: `meshRegistry`-backed converted meshes ("Convert to Mesh") aren't in the DTO yet, so a reload falls back to the existing placeholder-cube path for those nodes — no worse than before (everything was in-memory-only), and proper mesh persistence is H1 scope. Verified live: created a node with a distinctive transform, confirmed it round-tripped through a real `location.reload()` with a clean undo stack; "New Project" also autosaves the cleared state correctly.
- **Lights subnav empty/not opening (user-reported):** root cause was NOT the DOM/command registration (which was correct) — it's a `popover="auto"` element default: the browser's UA stylesheet applies `overflow: auto` to open popovers, which clipped the absolutely-positioned (`left-full`) hover-flyout submenu that intentionally renders outside the popover panel's own box. `ContextMenu.tsx`'s viewport-menu flyouts don't hit this because that component's overlay isn't itself a `popover` element. Fixed by adding `overflow-visible` to the per-menu popover div in `MenuBar.tsx`. Verified live at a real desktop viewport size (1400×900 — the tool's "desktop" preset turned out to be a much smaller native pane, which is what made the bug hard to pin down at first): confirmed the popover's overflow is no longer clipping, the flyout renders all 6 light entries, and clicking "Spotlight" creates the light node.
- **Follow-up (user-reported, screenshot):** even with overflow fixed, the flyout was visually offset from the "Lights" row by a 13px dead zone the mouse couldn't cross without losing hover. Cause: daisyUI's `.menu` component applies automatic left-margin indentation to any nested `<ul>` (for its own native accordion-style submenus) — a plain CSS descendant match, so it silently applied to the flyout `<ul>` too even though it isn't a `.menu` itself and is absolutely positioned, not indented in-flow. Fixed with `ml-0` on the flyout. Verified live: `flyout.left - li.right` is now exactly `0`, confirmed via `Point` light creation through the (now gap-free) flyout.

## Post-round: default-light disable + light/camera viewport helpers (pulled forward from M3/F4)

- **Default lighting rig disables itself once the document has its own lights.** `ViewportSystem`'s fallback ambient+key+fill rig is now toggled per frame via `!this.sync.hasLights` (`SceneSynchronizer.hasLights`, a cheap counter maintained on node add/remove — no per-frame scene scan). Structured so a future "environment" check (dome light, E5) is a one-line addition to the same condition.
- **Light/camera viewport helpers**, secondary-theme-color wireframes, new `src/render/helpers/` module (`CameraHelper.ts`, `LightHelpers.ts`):
  - **Camera:** wireframe pyramid, apex at the camera's origin, base on a fixed focus plane, local -Z (three's camera-forward convention) — a child of the camera node's Object3D so it follows rotation for free.
  - **Spotlight:** cone (base circle + 8 spokes), angle from `data.angle`, height mapped from intensity (`0.15·√intensity`, clamped) — attached as a child of the `SpotLight`, rebuilt whenever angle/intensity/type changes (`SceneSynchronizer.attachLightHelper`).
  - **Area light:** rect sized to `data.width`×`data.height` + 4 short corner ticks pointing in the emission direction (-Z) — child of the `RectAreaLight`, rebuilt on width/height change.
  - **Point/directional/ambient/hemisphere:** 64px-diameter unfilled circle, billboarded to face the camera every frame with a screen-constant size (same distance/fov math as the selection outline). Not a child of the light (billboarding can't just inherit the light's own rotation) — tracked in `SceneSynchronizer.lightBillboards`, positioned from the light's world position and updated in `updateHelperBillboards()` (called per pane, alongside `updateOutlines`).
  - All helpers are non-pickable (`raycast = () => {}`) and tagged `frustumCulled = false`.
- **Bug found + fixed during verification:** three's WebGPU backend doesn't draw `LineLoop` primitives at all (confirmed via direct canvas pixel sampling — a `LineLoop` circle was present in the scene graph with correct transform/material but produced zero rendered pixels, while an identical circle built as `LineSegments` rendered correctly). Both circle helpers (spotlight cone base, light billboard) were rewritten to build explicit `LineSegments` pairs instead of `LineLoop`. Separately, the billboard circles were also being frustum-culled incorrectly (likely the same Line-vs-culling gap in the WebGPU backend) — fixed by setting `frustumCulled = false` on every helper line object; cheap enough that always-render is a non-issue.
- **500-line rule enforcement:** extracting the helpers pushed `SceneSynchronizer.ts` over 500 lines; the selection-outline system (self-contained, untouched by this round otherwise) was split out to `src/render/scene-sync/SelectionOutline.ts`.
- Verified live: created one of each light type + a camera via the document API, confirmed via object-graph inspection (type, children, position, quaternion, scale) and direct canvas pixel sampling that every helper shape renders in the secondary theme color; confirmed `hasLights` flips the default rig's visibility both ways (lights added → default rig off; all lights removed → default rig back on).

## Post-round: 6 targeting/visibility/direction bugs in the light+camera helpers

- **Bug 1 (rotating an untargeted spotlight had no lighting effect):** three shines spot/directional lights at `.target.position` in world space and completely ignores the light object's own rotation. Fixed: `buildLightObject` gives every Spot/Directional light a private, never-parented `userData.autoTarget` Object3D, always assigned to `.target`. Each frame, `applyTargets()` re-points it along the node's own world direction when no target node is set — so rotating an untargeted spot/infinite light now actually changes where it shines.
- **Bug 2 (a targeted spotlight's rotation/helper didn't follow the target):** `applyTargets()` now also re-orients the light object itself (not just `.target`) toward a real target node, so the cone/line helper (a child, inheriting rotation) visually tracks the target too.
- **Root cause shared by bugs 1+2+4 — `Object3D.getWorldDirection()` and `Object3D.lookAt()` do NOT use the same "-Z is forward" convention as `Camera`'s overrides of the same methods in this three.js version:**
  - `Camera.getWorldDirection()` negates the base result; plain `Object3D`/`Light` does not — so `spotLight.getWorldDirection()` pointed exactly backwards relative to every helper's -Z-forward geometry. Fixed by negating explicitly where a non-Camera object's forward is needed.
  - `Object3D.lookAt()` swaps its eye/target argument order for anything that isn't `isCamera`/`isLight` — so calling `.lookAt(targetPos)` on a camera _node_ (a plain `Group`, not a real `THREE.Camera`) pointed local +Z at the target instead of -Z, exactly reversing the camera pyramid (bug 4, user-reported "pointing in the opposite direction"). Fixed with a new `SceneSynchronizer.lookAtForward()` that always replicates the Camera/Light convention via a manual `Matrix4.lookAt()`, used for every target-following object regardless of type.
  - Verified live via direct scene-graph geometry inspection (not just visual screenshots, which don't reliably surface a sign flip): confirmed the spotlight cone's world-space axis direction now matches `target.position - light.position` exactly, both with and without an explicit target node, and confirmed the camera pyramid's base corner now lands on the same side as an assigned target instead of the opposite side.
- **Bug 3 (infinite/directional lights needed a direction line, not a circle):** moved `"directional"` out of `BILLBOARD_TYPES` into the oriented-helper dispatch; added `buildDirectionalHelper()` — a single 1.5-unit line along local -Z, attached as a child like the cone/rect helpers.
- **Bug 5 (visibility toggled off in the Object Manager came back on after a reload):** `addNode()` built every fresh Object3D (mesh/light/camera/null) without ever applying `node.visible` — visibility was only synced in `updateNode()`, which never runs during initial construction. Since `rebuildAll()` (used by both `loadDTO()`/autosave-restore and "New Project") re-creates every node via `addNode()`, a persisted `visible: false` was silently dropped on every reload. Fixed with one line: `obj.visible = node.visible;` in `addNode()`. This was general (any node kind), not lights-specific — verified with a hidden directional light surviving a real `location.reload()` still hidden.
- **Bug 6 (default light shouldn't have a helper):** already true by construction — `ViewportSystem`'s fallback ambient/key/fill lights are plain `THREE.Light` instances added directly to the scene, never routed through `SceneSynchronizer.buildLightObject`/`attachLightHelper` at all. Confirmed via a scene-graph traversal (zero stray helper objects) rather than changing anything.

## Post-round: gizmo layout for ortho views, target-clear PSR retention, hidden-object picking

- **Bug 2 (gizmo unusable in top/side ortho views — perpendicular rotation rings obscure the move handles):** user supplied `BetterTransformGizmo.ts` as a reference (kept untracked; ideas adapted into the existing gizmo, not swapped in — the reference has no scale handles). Reworked the radial layout so **scale cubes sit inside the rings (r=0.5), rotation rings at r=1.0, move arrowheads outside (r=1.4)**, and added a hit-test **precedence** (`HANDLE_PRIORITY`: scale > translate > rotate, ties broken nearest-first) applied via a new `pickHandle()` used by both `pointerDown` and `updateHover`. In an edge-on ortho view the projected ring lines no longer steal the move/scale clicks. Verified by driving the real `pointerDown → pickHandle` path with synthetic raycasts at each handle's projected screen position in a **top ortho pane**: X-move→translate:X, Z-move→translate:Z, X-scale-cube (which overlaps the edge-on ring)→scale:X, Y face-on ring→rotate:Y; and confirmed no perspective regression (Z/X rings still grab as rotate, arrows still translate).
- **Bug 1 (removing a target should retain the object's current PSR, not snap back):** a look-at constraint only ever drove _rotation_ (P/S untouched), and `applyTargets()` overrides the live object each frame without writing to the doc — so clearing the target reverted to the stale stored rotation. `TargetSelector`'s "None" path now **bakes** the orientation the object is currently showing into `node.transform.rotation` (position/scale carried through unchanged) in the _same_ transact that removes the target → one "Clear Target" undo step. The current rotation is read via a narrow render→UI bridge: `SceneSynchronizer.currentLocalRotation(id)` (the live `Object3D.rotation`, which `applyTargets`/`lookAtForward` keeps as the followed local euler), exposed through `targetRotationBakerAtom`. Verified end-to-end through the real Attributes `<select>`: set target → light follows; clear → node + live rotation stay at the followed value (no snap), pos/scale preserved; undo restores both the target and the original rotation.
  - **jotai gotcha fixed mid-verification:** a primitive atom interprets a _function_ value passed to `store.set` as a state-updater and _invokes_ it (`fn(prevNull)`), so storing the baker function bare left the atom null and the bake silently no-op'd. Wrapped it as `{ bake }`. (Only caught because the live browser test showed the object snapping despite `currentLocalRotation` returning the right value in isolation.)
  - **Scope (deferred):** deleting the target _object_ (via `RemoveNodeCommand`) also strips the constraint and will still snap the referrers back — that path isn't intercepted. The reported/primary flow (the selector "None") is fixed; the delete-the-target case is a known follow-up (needs the delete to scan referrers and bake each in the same transaction).
- **Bug 3 (hidden objects were still right-clickable / selectable in the viewport):** three's raycaster ignores `Object3D.visible` (confirmed by reading `Raycaster.js` — no visibility check), and a hidden _ancestor_ never sets `.visible=false` on descendants, so picking has to consult the document. Added `SceneSynchronizer.visibleNodeIdOf()` which resolves the hit's node id only if that node **and every ancestor node** is visible; `ViewportInput` now iterates hits and takes the first that resolves to a visible node, for **both** click-select and the context menu (same latent bug in both). Verified: a hidden cube still produces raw raycast hits but `visibleNodeIdOf` returns null, so it's skipped.
